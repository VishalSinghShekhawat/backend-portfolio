Reducing API Response Time from 3–10 Seconds to Under 1 Second

Backend performance optimization · Node.js, TypeScript, Amazon DocumentDB, Redis

The challenge

An education platform had a course-listing API that combined data from three collections to build the response its frontend needed. As the dataset grew from hundreds to thousands of courses, response times typically reached 3–4 seconds and could climb to 10 seconds for complex publishing-status filters.

The API fetched data from every collection and did most of the processing in application code. That work already ran in a separate worker, but the real problem remained: the API retrieved and processed far more data than any single page needed.

The goal was backend-driven pagination and filtering that kept course-level uniqueness, business-unit-specific data, and publishing rules intact.

Why it was hard

Pagination across multiple collections

One course can have several detail records across business units, but the frontend needs one row per course. Paginating raw detail records produces duplicate courses and wrong page contents.

Publishing rules spanning two data sources

A course’s effective status depended on a user-managed publishing status and on an end date held elsewhere. Queries also had to respect terms, so records from one term never mixed with another.

Unnecessary data retrieval

Fetching every detail record before filtering became slower with each new course, even when a user only wanted the newest few.

The solution

Two query paths instead of one

Filtered and unfiltered requests have different shapes, so each gets its own path.

Before: application-heavy processing

  1. Fetch data from all three collections
  2. Merge and deduplicate large datasets in application code
  3. Several seconds; complex filters could reach 10 seconds

After: a path for each kind of request

No detail filters

  1. Query the course master
  2. Paginate, then fetch only the needed details

With detail filters

  1. Filter details with $match
  2. Group by course and term with $group
  3. Sort and paginate the course list
800 ms or lessObserved after optimization in tested scenarios

Filtering and grouping in the database

For filtered requests, aggregation does the heavy lifting before results reach the application. A simplified version of the pipeline:

[
  { $match: { /* requested filters */ } },
  {
    $group: {
      _id: {
        courseId: "$courseId",
        term: "$term"
      }
    }
  },
  { $sort: { /* required ordering */ } },
  { $skip: offset },
  { $limit: pageSize }
]

Grouping by course ID and term before $skip and $limit means each page counts unique courses, not detail records. I used targeted queries and aggregation without $lookup, because it wasn’t needed for this design and the DocumentDB environment constrained the available options.

Simplified publishing-status queries

The publishing filter needed data kept in two places. I moved the end date and published-term metadata into a dedicated field on the details records, and only the master-data update API may change it. Queries are built around the exact course and term combinations needed, so unrelated terms are never fetched.

Redis for reference data, indexes for the query patterns

Center names come from a small, stable master dataset. I served them from Redis and refreshed the cache whenever the master-data update ran, which removed a repeated database read from every listing request.

I also added indexes based on the API’s query and filtering patterns, so retrieval stays efficient as the data grows. With these changes, the separate worker was no longer needed for this API.
