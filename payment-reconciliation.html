When the Payment Succeeds but the App Never Hears About It

Payment reconciliation design · Node.js, TypeScript, MongoDB

An hourly reconciliation job works alongside gateway callbacks to recover eligible missed payment updates automatically.

The problem

Payment processing is not a single API call. A payment can reach the gateway even when the application never receives the response. A callback can arrive late, a database update can fail, or a transaction can sit in a pending state longer than expected.

Before this workflow, gaps like these tended to surface through customer support tickets. We were building a new payment-gateway integration for an order-management system, and it needed a way to find and fix these gaps without waiting for a customer to complain.

Payment processing is a state-management and consistency problem, not just a request-and-response problem.

The core design idea

An order and its payment attempts are different things. The order is the customer’s purchase and its business status. A transaction is one payment attempt, with its own gateway transaction ID, status, and gateway response. One order can have several attempts, and a failed or unresolved attempt does not mean the order has failed for good.

Keeping the two states separate makes partial failures easier to reason about. A transaction can succeed while the order update fails, and the design has to leave room to spot and recover that.

The solution: two ways for an update to arrive

Order created → payment attempt → transaction initiated

Callback (fast path)

Gateway notifies the app

  1. Decrypt payload and verify signature
  2. Find the existing transaction
  3. Skip if already completed
  4. Update the transaction

Reconciliation (safety net)

Runs hourly

  1. Select eligible failed and pending transactions
  2. Ask the gateway for the status using the existing transaction ID
  3. Update the transaction
  4. If one lookup fails, continue with the rest
  1. On a successful payment, the order is marked completed

The callback gives a quick update. The hourly job catches what the callback missed. The job handles two groups separately: failed transactions from the preceding 24-hour window that have passed an age threshold, and pending or processing transactions in the reconciliation window that may still succeed.

A concrete scenario

  1. A customer completes payment, and the gateway records it as successful.
  2. The callback does not update the application, so the transaction remains unresolved locally.
  3. The next eligible reconciliation run queries the gateway using the existing transaction ID, receives the successful status, and updates the transaction and order.

This illustrates the recovery path when the transaction is eligible for reconciliation and the gateway returns a usable status.

Branch-specific gateways

Different branches can use different gateways with their own credentials. The backend checks that the chosen gateway is configured for the requested branch and that the branch in the request matches the one on the order. Credentials are fetched using that validated context, database access is restricted, and sensitive values are redacted from logs.

Key decisions

  • Check the status; don’t retry the payment. Reconciliation reuses the existing transaction ID to learn the outcome of a payment that already exists. Checking an outcome and starting a new charge are different operations.
  • Callbacks for speed, reconciliation for safety. The callback avoids waiting for the next scheduled run; the scheduled run recovers updates the callback missed.
  • Keep transaction state apart from order state. A payment can succeed while the order update fails, and separating the two makes those cases visible.
  • Trust stored data, not client input. Branch and gateway come from the stored transaction and order, giving callbacks a reliable reference to check against.
  • One bad lookup shouldn’t stop the run. If a single gateway lookup errors, the job moves on to the remaining transactions.

Engineering approach

Payment reliability depends on more than receiving a successful gateway response. The application needs to connect that response to the correct transaction and order, validate the source, and keep status updates moving even when an individual lookup fails.

  • Reason about the full transaction lifecycle. Treat each payment attempt as its own transaction while keeping the order’s business status distinct.
  • Design for more than one update path. Combine gateway callbacks with scheduled reconciliation so a missed callback does not have to be the end of the recovery process.
  • Validate against trusted transaction context. Use the stored order, branch, and gateway association when validating incoming updates.
  • Identify the next reliability improvement. For evolving requirements, evaluate idempotency, safe state transitions, and consistency checks against the actual failure modes and business needs.
